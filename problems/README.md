# AHC 練習問題集 (40 問) — ライブラリの実戦テスト

`AHC Library` の 4 つのライブラリ (貪欲 / 山登り・焼きなまし / ビームサーチ / モンテカルロ) を
実際に使って解くための練習問題集です。AHC の 4 時間コンテスト程度の難易度を目安にしています。

各 `.cpp` の先頭コメントに次が書いてあります。

- **【問題】** 問題文
- **【入力】【出力】【スコア】** 入出力形式と採点
- **【入力生成方法】** テストケースの作り方 (プログラム内にも実装済み。標準入力が無ければ自動生成する)
- **【解法】** 次の 7 項目で解き方を説明している (1 問あたり 30〜40 行)
  - `● 考え方` … 問題をどう捉えるか。なぜその手法なのか
  - `● 状態 (State)` … 何を持つか。なぜそれで足りるか
  - `● 手の作り方` … 候補 / 近傍の作り方と、絞り込みの理由
  - `● 評価値` … 何を基準に選ぶか。式とその式にした理由
  - `● 差分計算 / 高速化` … どこを O(1) や O(deg) にしたか
  - `● つまずきポイント` … 実際に踏んだバグと、気付いたきっかけ
  - `● さらに伸ばすなら` … 次の一手、または上限に達している根拠
- **【改善】** 初版から何を変えて何 % 良くなったか (改善作業をした問題のみ)
- **【採用したライブラリ】** そのカテゴリのどのライブラリを使ったか + 実測比較

## 使い方

```bash
cd problems/greedy
g++ -std=c++20 -O2 -o a.out 01_multi_vehicle_orienteering.cpp
SEED=0 ./a.out > out.txt        # 標準入力が無ければ SEED から問題を内部生成する
SEED=1 ./a.out > out.txt        # 別のテストケース
echo "..." | ./a.out            # 自分で作った入力を与えることもできる
```

stderr に次が出ます。

| 行 | 意味 |
|---|---|
| `Score = ...` | そのケースのスコア（出力を再生して計算した真の値） |
| `[verify] ...` | **1 手ずつの自動検証**（焼きなまし系は差分計算、ビーム系はハッシュと候補数） |
| `[check] ...` | 積み上げたスコアと、出力を再生した真のスコアの突き合わせ |

`[check]` は「最後の値」しか見ないので、**却下された手の差分計算が間違っている**、
**`apply_move` が `score` を上書きして誤りを隠している**、といったバグを見逃します。
そこで焼きなまし系・ビーム系には `[verify]` を入れてあり、
1 手ずつ「`calc_score` の返り値 対 実際に適用して全計算し直した変化量」
（ビーム系は「`calc_hash` 対 `apply_move` 後の hash」と「候補数 ≤ `MAX_BRANCH`」）を突き合わせます。
乱数の状態は前後で復元するので、検証を入れても探索結果は 1 ビットも変わりません。
提出時に外したければ `VERIFY_MOVES = 0` にしてください。

**それでも `[verify]` と `[check]` の両方が通っても A/B 比較は必要です。**
実際に、打ち切り条件を間違えた `calc_score` が `apply_move` 側で厳密値を入れ直していたため
両方をすり抜け、A/B 比較の悪化で初めて発覚した例があります。

パラメータは環境変数 `p1, p2, ...` で上書きできるので、各ライブラリの `optimize.py` を
コピーしてくれば optuna でそのまま調整できます。

## 付属ツール

```bash
python3 eval.py FILE.cpp --seeds 0,1,2            # スコアを測る
python3 eval.py FILE.cpp --env p1=2.0,p2=0.3      # パラメータを変えて測る
python3 eval.py --ab BASE.cpp CAND.cpp --seeds 0,1,2,3,4   # 2 案を seed ごとに交互実行して比較
python3 retarget.py SRC.cpp KIND DST.cpp          # 同カテゴリの別ライブラリへ問題部分を移植
```

`--ab` は **必ず使ってください**。実行は毎回 1.9 秒使い切るので、マシンの負荷で反復回数が変わり、
別々に測った数字を比べると簡単に誤った結論に至ります。交互実行なら負荷の偏りが相殺されます。

## ライブラリの選び方について

各問題は、そのカテゴリのライブラリを**全種類**実際に走らせて、一番スコアが良かったものを採用しています
(各ファイルの【採用したライブラリ】に実測比較が載っています)。
同じ問題定義をそのまま別のテンプレートに貼れる設計なので、自分の問題でも同じように総当たりして選ぶのが確実です。

**まず一番単純なもの (単純貪欲 / 山登り / ビームサーチ / 素のモンテカルロ) で組んで `[check]` を通し、
それから他のバリアントに貼り替えて比べる**のが安全で速い進め方です。

## カテゴリ横断の検証

「別のカテゴリで解いた方が明らかに強いのでは?」という観点でも実装して比べ、結果に応じてカテゴリを移しました。

| 問題 | 検証内容 | 結果 | 対応 |
|---|---|---|---|
| 多次元ナップサック | 焼きなまし (追加/削除/入れ替え近傍) で実装して比較 | 貪欲 18277 / 焼きなまし 18128 → **貪欲が上** | 貪欲系のまま |
| センサー配置 | 焼きなまし (センサーを 1 個動かす近傍) で実装して比較 | 貪欲 26183 / 焼きなまし 26991 → **焼きなましが 3.1% 上** | **焼きなまし系へ移動** |
| 配送センター立地 (k-median) | 貪欲 (施設を 1 個ずつ追加) で実装して比較 | 焼きなまし 1606085 / 貪欲 1606676 → **ほぼ同点** | 実装が単純な**貪欲系へ移動** |

その他の問題については次の理由からカテゴリが妥当と判断しています。

- **貪欲系**: 解が「操作の列」として構築されるもの、局所変更が実行可能性を壊すもの、評価が重くて反復数を稼げないもの
- **焼きなまし系**: 完成解が最初から手元にあり、小さな入れ替えで壊れずに動かせるもの (割当・順列・配置)
- **ビームサーチ系**: 「1 ターン 1 手」の逐次決定で後戻りできないもの
- **モンテカルロ系**: **未来が確率的で、決めた時点では結果が分からない**もの。他の 3 カテゴリでは原理的に扱えない

## 改善作業でわかったこと

40 問すべてについて「テンプレートは変えずに、パラメータと 6 節 (問題ごとに書き換える部分) だけを直す」
という条件で改善を試みました。効いた順に並べると次の通りです。

1. **評価関数の設計ミスを直す** — 一番効く。
   ジョブ割当は ATC 則 (納期余裕で減衰させた単価/処理時間) にしただけで -99%、
   エレベーターは「乗車人数ボーナス」が待ちコストとちょうど相殺して
   「乗せたまま走り回るのがタダ」になっていたのを 0 にして -32%。
2. **合法手を取りこぼしていないか確認する** — 農場経営は所持金判定がそのターンの収穫を反映しておらず、
   合法な植え直しを探索できていなかった (直して +429%)。
   アイテム合成は「損なレシピでも実行可能なら必ず打つ」構造で初期在庫より価値を減らしていた (+97%)。
3. **近傍を「効く手」に絞る** — 多群数分割は近傍を「最大和群↔最小和群の交換」だけにして -99% (理論下限に到達)。
   CVRP は移動先を近い顧客のとなりに限定して採択率 6%→20%。
   順列整列は「差分が改善する反転」だけを候補にして候補数 300→15。
4. **差分計算・状態表現の高速化** — 反復数が 5〜10 倍になる。ただし
   「時間を 10 倍にしてもスコアが変わらない」問題では効かない (先に確かめること)。
5. **シナリオ生成をほんとうの分布に合わせる** (モンテカルロ) — 蓄電池は未来価格を「今日の価格」ではなく
   初日の定数から生成していた。タクシーはシナリオが a≠b 制約を落としていた。

一方、**次の 8 問は既に上限に到達していることを確認したので変更していません** (無理な変更を入れると悪化するため)。
多次元ナップサック・k-median・センサー配置・円詰め込み・ダンジョン扉・待ち行列・天候工程・グラフ分割。
いずれも厳密解 (MILP / DP / 完全先読み上界) を別途計算して、既存実装が最適または最適の 99% 以上であることを確認しています。
