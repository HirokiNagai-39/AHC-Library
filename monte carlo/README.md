# AHC 用 モンテカルロ法ライブラリ

未来が確率的に決まる問題向けの、**単一ファイル・コピペ可能**なモンテカルロ法テンプレートです。
「今この手を選んだら最終的に平均どれくらいのスコアになるか」を、ランダムな未来（シナリオ）を
何本も試して見積もり、**期待値が最良の手**を選びます（MCTS ではなく、候補ごとの期待値評価）。

```
monte carlo/
├── 1_monte_carlo/          全候補が必ず同数のシナリオを試す完全公平版
├── 2_successive_halving/   フェーズごとに下位候補を切り、有望手にシナリオを集中させる版
│    ├── main.cpp           ← 本体（これだけ提出する）
│    ├── optimize.py        ← optuna によるパラメータ自動調整
│    └── pahcer_config.toml ← pahcer の設定
└── tools/
     ├── gen.py             デモ用テストケース生成
     ├── in/  out/
```

---

## 1. すぐ動かす

デモは **オンライン箱詰め**です。K 個の箱（容量 CAP）に、毎ターン来るアイテム（大きさ s・価値 v は
ランダム）をどれかの箱に入れるか捨てる。**未来のアイテムは分からず、分布だけ分かっている**状況で、
入れた価値の合計を最大化します。標準入力が無ければランダム生成するのでそのまま動きます。

```bash
cd 1_monte_carlo
g++ -std=c++20 -O2 -o a.out main.cpp
./a.out < /dev/null > /dev/null
# Score = 6537
# rounds = 1987825, rollouts = 7783393, scenarios/turn = 0..767453, time = 1881.1 ms
# [check] running = 6537 / replay = 6537
```

`[check]` は **実装のバグ検出用**です。探索中に積み上げたスコアと、出力した手を最初から再生した
スコアが一致するはずです（再生時に容量オーバーがあればエラーを出します）。

## 2. 2 つの手法と効果

| | 手法 | どういう時に使うか | 主なパラメータ |
|---|---|---|---|
| 1 | モンテカルロ法 | **まずこれ**。全候補が必ず同数のシナリオを試すので比較が完全に公平 | rollout の方策, 時間配分 |
| 2 | 逐次絞り込み | 候補数が多いとき。弱い候補を早く切って有望手にシナリオを集中できる | ＋絞り込みの強さ |

デモ（3 ケース合計、価値の合計なので**大きいほど良い**、1 ケース 1.9 秒）：

| 手法 | スコア合計 | 貪欲比 |
|---|---|---|
| 貪欲（シナリオ 1 本だけ = `MAX_SCENARIO=1`） | 10590 | — |
| 1 モンテカルロ法 | 14761 | **+39%** |
| 2 逐次絞り込み | **15095** | **+43%** |

`MAX_SCENARIO=1 ./a.out` で「シナリオ 1 本 = ほぼ貪欲法」になるので、
**モンテカルロがどれだけ効いているか**をいつでも測れます。

## 3. ★シナリオを公平にするための 4 原則★

このライブラリの核心です。**候補の比較が不公平だと、シナリオを何本回しても正しい手は選べません。**

1. **1 ラウンドで作ったシナリオは全候補で使い回す（共通乱数法）**
   候補ごとに別のシナリオを引くと「運の良い未来を引いた候補」が勝ってしまいます。
   同じ未来で比べれば運の要素が相殺され、候補間の差だけが残ります。
2. **シナリオは「ターン番号で引ける配列」にする**
   乱数を消費順に引く実装にすると、候補によって行動が変わった瞬間に未来そのものが変わります。
   `sc.s[t]` のようにターン番号でアクセスできる形にしてください。
3. **rollout 内の方策がランダムなら、その乱数も候補間で同じ種から始める**
   本ライブラリは方策用の `Xor128` をラウンドごとに 1 つ作り、候補ごとにその**コピー**を渡します。
4. **打ち切りは必ずラウンド境界で行う**
   ラウンドの途中で時間切れにすると、候補ごとにシナリオ数が変わって比較が壊れます。
   本ライブラリは「直近 1 ラウンドの実測時間 × 1.1 が残り時間に収まるか」で判定して打ち切ります。

> 全候補のシナリオ数が必ず等しくなるので、**平均を取らず合計のまま比較できます**（除算不要）。

### 効果の実測

同じデモで、原則 1 だけを崩した版（候補ごとに別シナリオを引く）と比べた結果：

| | スコア（3 回実行） | 平均 | 1 ターンあたりのラウンド数 |
|---|---|---|---|
| 公平（共通乱数法） | 6464 / 6517 / 6483 | **6488** | 167 万〜212 万 |
| 不公平（候補ごとに別シナリオ） | 6360 / 6191 / 6157 | 6236 | 140 万〜160 万 |

**スコアで約 4% 差**がつきます。しかも共通乱数法はシナリオ生成が 1 ラウンド 1 回で済むので
**ラウンド数自体も 3 割ほど多く回せます**（精度と速度の両方で得をします）。

## 4. 書き換えるのはここだけ

```cpp
struct Move     { int8_t box; };           // 手
struct State    { float score; ... };      // ★float score 必須
struct Scenario { uint8_t s[MAXT], ...; }; // 未来の不確定要素 1 本ぶん（★ターン番号で引ける配列に）

void  init_state(State &s);                          // 初期状態
int   enum_moves(const State &s, Move *out);         // 今の候補手を全列挙して個数を返す
float calc_score(const State &s, const Move &mv);    // その手で確定するスコア差分
void  apply_move(State &s, const Move &mv);          // 手を適用する（score は触らない）
void  gen_scenario(Scenario &sc, Xor128 &rnd, int from);      // シナリオを 1 本作る
float rollout(State &s, const Scenario &sc, Xor128 &rnd);     // 最後までシミュレートして最終スコアを返す
```

- `rollout` に渡る `State` は**作業用コピー**なので好きに壊して構いません
- `rollout` は **速さが全て**です。方策は貪欲など軽いものにしてください
  （1 ターンあたり数千〜数十万回呼ばれます）
- `MAX_CAND` は 1 ターンの候補手の最大数。配列サイズに直結するので必ず正しい値にしてください

## 5. 最大化 / 最小化 の切り替え

```cpp
constexpr bool MAXIMIZE = true;        // ← スコア最大化（デモはこちら）
// constexpr bool MAXIMIZE = false;    // ← スコア最小化
```

`if constexpr` で分岐が消えるので実行時コストはゼロです。
`optimize.py` の `get_direction()` と `pahcer_config.toml` の `objective` も合わせてください。

## 6. パラメータ調整（optuna + pahcer）

C++ 側は環境変数 `p1, p2, ...` を読み、無ければ既定値を使います。**そのまま提出して大丈夫です。**

```bash
python3 tools/gen.py 0 20
cd 1_monte_carlo
vim pahcer_config.toml
python3 optimize.py
```

| キー | 意味 |
|---|---|
| `p1` | `ROLLOUT_TH` … rollout の方策のパラメータ（**問題ごとの方策の重みに置き換える**） |
| `p2` | `TIME_ALPHA` … ターンごとの時間配分。0 = 均等、大きいほど序盤に厚く配分 |
| `p3` | `HALVE_RATE`（逐次絞り込み版のみ）… 1 フェーズごとに候補を 1/`HALVE_RATE` に絞る |
| `MAX_SCENARIO` | シナリオ数の上限。既定は実質無制限。`1` にすると貪欲法相当（比較用） |

**rollout の方策こそが最大のチューニング対象**です。方策が賢いほど期待値の見積もりが正確になり、
方策が軽いほどシナリオを多く回せます。この 2 つのトレードオフを `p1` などで調整します。

## 7. 高速化のためにやっていること

| 箇所 | 内容 |
|---|---|
| シナリオ生成 | 1 ラウンドに **1 本だけ**作って全候補で共有。生成コストが候補数で割れる（公平性の副産物） |
| シナリオの範囲 | `gen_scenario(sc, rnd, from)` で**残りターンぶんだけ**生成。終盤ほど生成が軽くなる |
| 状態の作り置き | 候補を適用した直後の状態を 1 ターンに 1 回だけ作り、rollout ごとにそこからコピー |
| メモリ確保 | 候補・状態・シナリオはすべて静的確保。探索ループ中に `malloc` を一度も呼ばない |
| 期待値の集計 | `double` で加算（`float` だと数万回の加算で精度が落ちて比較が壊れる） |
| 比較 | 全候補のシナリオ数が等しいので**合計のまま比較**（除算なし） |
| 絞り込み | 逐次絞り込み版は全ソートせず `nth_element` で上位だけ残す |
| 時間計測 | rdtsc / cntvct 直読み。**1 ラウンドに 1 回**だけ。直近ラウンドの実測時間で次が入るか判定 |
| 時間配分 | ターンごとの締切を**累積**で持つので、早く終わったターンの余りが自動的に後ろへ回る |

## `[check]` について

`[check]` は「進行中に積み上げたスコア」と「出力を再生した真のスコア」を比べます。
最終ターンの実現値も `reveal_turn(state, T)` で反映してから比較するので、**両者は完全に一致するはず**です。
ずれていたら `calc_score` / `apply_move` / `reveal_turn` のどれかが間違っています。

なお `rollout` の中で未来（`TRUE_*` 配列）を覗いてしまうバグは、この `[check]` では検出できません
（覗いた方がスコアは上がってしまう）。`rollout` と `enum_moves` からは
**必ず `Scenario` 経由でしか未来を読まない**ことを、コードレビューで確認してください。

## 8. 注意点

- **`rollout` の重さが全て**：1 ターンあたりのシナリオ数はほぼ `1 ターンの持ち時間 ÷ (候補数 × rollout の時間)` です。
  rollout を 2 倍速くすればシナリオが 2 倍回せます。
- **候補数が多いとき**：候補数 × rollout がラウンドのコストなので、候補が 50 個もあると 1 ラウンドが重くなります。
  そういう時は 2（逐次絞り込み）を使うか、明らかに悪い候補を `enum_moves` の時点で落としてください。
- **シナリオ数が足りているか**：stderr の `scenarios/turn` を見てください。数十本しか回っていないなら
  期待値の推定が荒すぎます（rollout を軽くするか、候補を減らす）。
- **未来を覗かない**：デモでは真のアイテム列を `reveal(turn)` 経由でしか読まないようにしています。
  自分の問題に移植するときも、未来の情報が漏れていないか必ず確認してください。
- **`float` の精度**：`State::score` は float ですが、期待値の集計は `double` です。
  スコアが 1e7 を超える問題では `State::score` も `double` にしてください。
- **`[check]` の running と replay は 1 ターンぶんずれる**：最終ターンの実現値は次の `reveal_turn()` で反映される作りなので、
  `running` は最後の 1 ターンぶん足りない値になります（仕様）。提出スコアは `Score = ...`（replay 側）を見てください。
  それ以上にずれていたら `calc_score` / `apply_move` / `reveal_turn` のどれかが間違っています。
- **応用（このライブラリの外）**：解全体を 1 つ決める問題（ターン制でない問題）では、
  「解を焼きなましで動かし、その評価をモンテカルロ平均で行う」形になります。
  その場合も**比較する解の間で同じシナリオ集合を使う**（共通乱数法）のが鉄則です。
