# AHC 用 局所探索ライブラリ（山登り・焼きなまし）

AHC でそのまま使える、**単一ファイル・コピペ可能**な局所探索テンプレート集です。
5 手法それぞれがフォルダ単位で独立していて、`main.cpp` の「■ 問題ごとに書き換える部分」だけを
書き換えれば動きます。パラメータは環境変数経由で **optuna + pahcer** から自動調整できます。

```
simulated annealing/
├── 1_hill_climbing/          山登り
├── 2_hill_climbing_kick/     キックあり山登り (Iterated Local Search)
├── 3_simulated_annealing/    焼きなまし
├── 4_multi_start_annealing/  多点スタート焼きなまし
├── 5_iterated_annealing/     焼きなましの繰り返し (リヒート)
│    ├── main.cpp             ← 本体（これだけ提出する）
│    ├── optimize.py          ← optuna によるパラメータ自動調整
│    └── pahcer_config.toml   ← pahcer の設定
└── tools/
     ├── gen.py               デモ(TSP)用テストケース生成
     ├── in/  out/
```

---

## 1. すぐ動かす

各 `main.cpp` にはデモとして **TSP（巡回セールスマン問題）** が入っています。
標準入力が無ければランダムに問題を生成するので、そのまま実行できます。

```bash
cd 3_simulated_annealing
g++ -std=c++20 -O2 -o a.out main.cpp
./a.out < /dev/null > /dev/null
# Score = 10564
# iter = 267861314, accept = 2289380 (0.85%), time = 1900.5 ms
# [check] diff-sum = 10564.414, full = 10564.688
```

`[check]` は **差分計算のバグ検出用**です。`diff-sum`（差分を足し込んだスコア）と
`full`（全計算したスコア）が大きくずれていたら `calc_score()` か `apply_move()` が間違っています。
（float の丸め誤差でごく僅かにずれるのは正常）

---

## 2. 5 つの手法の使い分け

| | 手法 | どういう時に使うか | 主なパラメータ |
|---|---|---|---|
| 1 | 山登り | まず最初に書く。差分計算の正しさ・反復回数の確認用。局所解で止まる | （近傍の選び方のみ） |
| 2 | キックあり山登り | 温度の調整が難しい / スコアが離散的で温度を決めにくい問題 | キック強さ, 停滞判定回数 |
| 3 | 焼きなまし | **基本これ**。AHC で最もよく効く | 開始温度, 終了温度 |
| 4 | 多点スタート焼きなまし | 初期解によって結果が大きくぶれる / 局所解が非常に多い問題 | 温度, スタート回数 |
| 5 | 焼きなましの繰り返し | 良い解の周辺を掘り直したい。多点スタートと違い解を捨てない | 温度, 繰り返し回数, 温度減衰率 |

デモ TSP（3 ケース合計、総距離なので**小さいほど良い**、1 ケース 1.9 秒）：

| 手法 | スコア合計 | 反復回数/実行 |
|---|---|---|
| 1 山登り | 34236 | 約 2.5 億 |
| 2 キックあり山登り | **32241** | 約 2.5 億 |
| 3 焼きなまし | 32357 | 約 2.7 億 |
| 4 多点スタート焼きなまし | **32199** | 約 2.7 億 |
| 5 繰り返し焼きなまし | 32352 | 約 2.7 億 |

> 1 秒あたり約 1.4 億回の遷移。どれが勝つかは問題次第なので、**同じ `State` / `modify` / `calc_score` を
> 5 つのフォルダにコピーして総当たりで比較する**のがこのライブラリの使い方です。

## 3. 書き換えるのはここだけ

`main.cpp` の「■ 6. ここから問題ごとに書き換える部分」の中身だけを書き換えます。

```cpp
struct State {
    float score;        // ★必須：現在のスコア
    int   ord[MAXN];    // ここから下は問題ごとに自由
};

void  init_state(State &s);   // ★必須：初期解構築（s.score も必ずセットする）
void  modify(State &s);       // ★必須：遷移(近傍)を1つ選ぶ ★ここでは state を変えない
float calc_score(State &s);   // ★必須：選んだ遷移を適用したときの「スコア差分」を返す
void  apply_move(State &s);   //        採用が決まった遷移を実際に state へ反映する
float full_score(const State &s); //    スコアの全計算（初期化・デバッグ用）
```

探索ループはこうなっています：

```cpp
modify(s);                          // ① 近傍を1つ選ぶ（まだ適用しない）
float diff = calc_score(s);         // ② その差分を計算
if (採用判定(diff)) {                // ③ 採用なら
    apply_move(s);                  //    実際に適用して
    s.score += diff;                //    差分を足し込む
}
```

**なぜ「選ぶ → 差分 → 採用時だけ適用」なのか**：焼きなましでは提案の 99% 以上が却下されます。
却下時に何もしないこの順序なら、却下パスのコストが「近傍を選ぶ＋差分計算」だけで済みます。

> 「先に適用して却下時に戻す」書き方にしたい場合は、`modify()` の中で適用まで行い、
> `apply_move()` を空にして、ループ内の `// else rollback(s);` のコメントを外してください。

## 4. 最大化 / 最小化 の切り替え

`main.cpp` の 4 節で、使う方だけ残してもう一方をコメントアウトします。

```cpp
// constexpr bool MAXIMIZE = true;     // ← スコア最大化のとき こちらを有効化
constexpr bool MAXIMIZE = false;       // ← スコア最小化のとき こちらを有効化
```

`if constexpr` で分岐が消えるので実行時コストはゼロです。
`optimize.py` の `get_direction()` と `pahcer_config.toml` の `objective` も合わせて切り替えてください。

## 5. パラメータ調整（optuna + pahcer）

C++ 側は環境変数 `p1, p2, ...` を読み、無ければ既定値を使います。**そのまま提出して大丈夫です。**

```cpp
float TEMP_START = 50.0f;   // p1: 開始温度
float TEMP_END   = 1.0f;    // p2: 終了温度
void load_params() {
    pick_env("p1", TEMP_START);
    pick_env("p2", TEMP_END);
}
```

手順：

```bash
python3 tools/gen.py 0 20          # テストケースを用意（実際の AHC では公式 tools を使う）
cd 3_simulated_annealing
vim pahcer_config.toml             # 問題に合わせて書き換え（採点方法・シード数など）
python3 optimize.py                # → best params = {'p1': 66.1, 'p2': 0.81, ...}
```

得られた値を `main.cpp` の既定値に書き戻して提出します。

- パラメータを増やすときは **`main.cpp` の `pick_env` のキーと `optimize.py` の dict のキーを必ず一致させる**
- 手動で 1 回試すだけなら `p1=100 p2=0.5 ./a.out < in.txt` でも上書きできます

### 温度の決め方の目安

- **開始温度** ≒ 「序盤に受け入れたいスコア悪化量の最大値」（＝遷移1回の差分の大きい方）
- **終了温度** ≒ 「終盤に無視したいスコア悪化量」（＝差分の最小値くらい。0 にはしない）
- 採用率（stderr の `accept`）が終盤で数 % 程度になるのが目安。0% なら温度が低すぎ、
  30% 以上なら高すぎです。

## 6. 高速化のためにやっていること

| 箇所 | 内容 |
|---|---|
| 乱数 | **xorshift128**。`[0,n)` の生成は剰余ではなく `(rnd * n) >> 32`（除算命令を使わない） |
| 時間計測 | x86 なら **rdtsc**、ARM なら **cntvct** を直読み（`chrono` の約 1/10 のコスト。実測 0.25ns vs 12ns）。<br>x86 では TSC 周波数を実行開始直後に自動較正するので環境依存がありません |
| 計測頻度 | **`ITER_PER_CHECK`（既定 1024）回に 1 回だけ**。内側ループには時間計測も温度更新も一切ありません |
| ブロック調整 | `ADAPTIVE_BLOCK`：1 ブロックの実行時間が `TARGET_BLOCK_MS`(0.5ms) になるよう回数を自動調整。<br>近傍が重い問題でも時間超過せず、軽い問題では計測回数を減らせます（固定にしたければ `false`） |
| 採用判定 | `exp()` を呼ばない。`exp(gain/T) > u` ⇔ **`gain > T * log(u)`** と変形し、`log(乱数)` を<br>4096 個の table（16KB = L1 に載る）に前計算。**乗算 1 回と比較 1 回**だけで判定します。<br>さらに改善時（`gain >= 0`）も右辺が負なので同じ式で真になり、分岐が 1 つで済みます |
| 最良解の保持 | `KEEP_BEST_FROM`（既定 0.5）：進捗 50% を過ぎてから最良解の記録を開始。<br>序盤の頻繁な `State` コピーを丸ごと省きます（`KEEP_BEST=false` で完全に無効化も可能） |
| その他 | 最大化/最小化・各種スイッチは `constexpr` + `if constexpr` で実行時分岐ゼロ。<br>`State` は `static` 領域に置いてスタック溢れを回避 |

## 差分計算の自動検証（`[check]` だけでは足りない）

`[check]` は「最後に積み上げたスコア」と「全計算したスコア」を比べるだけなので、次のバグを見逃します。

- **却下された手の `calc_score` が間違っている**（焼きなましでは大半の手が却下されるので、これが一番怖い）
- **`apply_move` が `score` を上書きしていて**差分の誤りが打ち消されている
- 誤差が偶然打ち消し合っている

いずれも「探索が静かに弱くなるだけで最後の値は合う」ため、スコアだけ見ていると気付けません。
そこで `main` の最初に `verify_diff()` が走り、1 手ずつ

```
calc_score() の返り値   対   実際に apply_move して full_score() を取り直した変化量
```

を突き合わせます。採用・却下に関係なく全部の手を調べるので、上の 3 つとも捕まえられます。

```
[verify] 差分計算 OK (200 手を全計算と突き合わせ)                          ← 正常
[verify] NG 4 手目: calc_score=-1088.98 / 実際の変化=-726.00 (ずれ 362.98) ← バグあり
```

- **乱数の状態は前後で復元する**ので、`VERIFY_MOVES` を変えても探索結果は 1 ビットも変わりません
- 数 ms しか掛からないので普段は付けたままで良い。提出時に消したければ `VERIFY_MOVES = 0`
- 検証中は必ず手を適用して先へ進みます（State の外（グローバル変数）に差分用の情報を持つ実装でも
  誤検出しないため）。ランダムウォークになるので初期解の周りだけでなく色々な状態を通ります
- 許容誤差は「全計算の float 丸め（合計値に比例）」＋「差分そのものの 0.1%」。
  合計値だけを基準にすると、合計が大きい問題で差分の誤りが埋もれます

※ それでも **`[check]` と `[verify]` の両方が通っても A/B 比較は必要**です。
実際に、打ち切り条件を間違えた `calc_score` が `apply_move` 側で厳密値を入れ直していたため
両方をすり抜け、A/B 比較の悪化で初めて発覚した例があります。

## 7. 注意点

- **`float` の精度**：`score` が 1e7 を超えるような問題では、差分を億回足し込むと誤差が溜まります
  （デモでは 2.5 億回で相対誤差 3e-5 程度）。`[check]` の 2 値がずれ過ぎるようなら
  `State::score` と `calc_score()` の戻り値を `double` に変えてください。
- **時間制限**：`TIME_LIMIT_MS`（既定 1900ms）は実行時間制限から余裕を引いた値にします。
  デモの実測では、プロセス起動・入出力込みで 1.92 秒でした。
- **`ITER_PER_CHECK`**：1 遷移が非常に重い問題（1 回 1μs 以上）では既定の 1024 でも
  最大 1ms 以上オーバーします。`ADAPTIVE_BLOCK=true` なら自動で縮みますが、
  心配なら初期値を小さくしてください。
- **`MAXN`**：デモは `MAXN=1000`（距離行列 4MB）。問題に合わせて必ず調整してください。
- **キックあり山登り**：既定のキックは「近傍遷移を `KICK_STRENGTH` 回、無条件に適用」という
  汎用実装です。問題専用のキック（TSP なら double bridge など）を書くとさらに強くなります。
