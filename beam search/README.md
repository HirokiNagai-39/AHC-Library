# AHC 用 ビームサーチライブラリ

AHC でそのまま使える、**単一ファイル・コピペ可能**なビームサーチ系テンプレート集です。
`main.cpp` の「■ 問題ごとに書き換える部分」だけを書き換えれば動きます。
パラメータは環境変数経由で **optuna + pahcer** から自動調整できます。

```
beam search/
├── 1_beam_search/               ビームサーチ（State をコピーする素直な実装）
├── 2_incremental_beam_search/   差分更新ビームサーチ（Euler tour / コピーしない）
├── 3_chokudai_search/           chokudai サーチ
│    ├── main.cpp                ← 本体（これだけ提出する）
│    ├── optimize.py             ← optuna によるパラメータ自動調整
│    └── pahcer_config.toml      ← pahcer の設定
└── tools/
     ├── gen.py                  デモ用テストケース生成
     ├── in/  out/
```

---

## 1. すぐ動かす

デモとして **グリッドお宝集め**（H×W の各マスに価値があり、(0,0) から毎ターン上下左右へ 1 マス動く。
初めて訪れたマスの価値をもらえる。T ターンでの合計を**最大化**）が入っています。
標準入力が無ければランダムに問題を生成するので、そのまま実行できます。

```bash
cd 1_beam_search
g++ -std=c++20 -O2 -o a.out main.cpp
./a.out < /dev/null > /dev/null
# Score = 3376
# turn = 600/600, expanded = 16559648, cand = 64342090, time = 1900.8 ms
# [check] eval = 3375.500 (探索が最大化した評価値) / true = 3376.000 (手順を再生した真のスコア)
```

`[check]` は **差分計算のバグ検出用**です。`eval`（探索中に差分で積み上げた評価値）と
`true`（出力した手順を最初から再生して計算した値）を比べます。
`calc_score` / `apply_move` / `undo_move` が間違っているとここがずれます。

時間が余ると `[hint]` が出るので、`BEAM_WIDTH` を上げる目安になります。

## 2. 3 つの手法の使い分け

| | 手法 | どういう時に使うか | 主なパラメータ |
|---|---|---|---|
| 1 | ビームサーチ | **まずこれ**。State が小さい（数百バイト以下）ならこれが一番速い | ビーム幅 |
| 2 | 差分更新ビームサーチ | State が大きい / コピーが重いとき。アルゴリズムは 1 と完全に同じ | ビーム幅 |
| 3 | chokudai サーチ | 時間を余らせたくない、ビーム幅を決めきれない、多様性が欲しいとき | 1 周の展開数 |

デモ（3 ケース合計、価値の合計なので**大きいほど良い**、1 ケース 1.9 秒）：

| 手法 | スコア合計 | 展開した状態数/実行 |
|---|---|---|
| 1 ビームサーチ | 7666 | 約 1300 万 |
| 2 差分更新ビームサーチ | 7661 | 約 1300 万 |
| 3 chokudai サーチ | **7798** | 約 780 万 |

> 1 と 2 は同じアルゴリズムなので結果もほぼ同じ（差は同点候補の選ばれ方の違い）。
> このデモでは chokudai が勝ちましたが、**どれが勝つかは問題次第**です。
> 同じ `State` / `enum_moves` / `calc_score` を 3 つのフォルダにコピーして比較してください。

### 差分更新版はいつ速いのか

`State` にダミー領域を足してサイズだけを変え、1.9 秒で展開できた状態数を測った結果：

| State のサイズ | 1 ビームサーチ | 2 差分更新 | 差分更新の速さ |
|---|---|---|---|
| 152 B | 1343 万 | 1338 万 | 1.00 倍 |
| 408 B | 1294 万 | 1344 万 | 1.04 倍 |
| 1176 B | 779 万 | 1344 万 | **1.72 倍** |
| 4248 B | 467 万 | 1344 万 | **2.88 倍** |

差分更新版は **State のサイズが変わっても速度が一切変わりません**（一度もコピーしないため）。
目安として **State が 1KB を超えたら差分更新版**、それ以下なら通常版で十分です。

## 3. 書き換えるのはここだけ

```cpp
struct Move  { int8_t dir; };            // 遷移(手)。小さいほど速い
struct State {
    float    score;   // ★必須：評価値（探索の順位付けに使う）
    uint64_t hash;    // ★必須（重複除去を使う場合）
    ...               // 問題ごとに自由
};

void     init_state(State &s);                        // 初期状態（score, hash もセット）
int      enum_moves(const State &s, Move *out);       // 遷移候補を全列挙して個数を返す
float    calc_score(const State &s, const Move &mv);  // その手を指したときの「スコア差分」
uint64_t calc_hash (const State &s, const Move &mv);  // その手を指したときのハッシュ（Zobrist）
void     apply_move(State &s, const Move &mv);        // 手を適用する（score は触らない）
void     undo_move (State &s, const Move &mv);        // apply_move を巻き戻す（★差分更新版のみ必須）
```

**フレームワークとの約束**

- 子のスコア = `親の score + calc_score(親, 手)` ← `score` はフレームワークが更新します
- `apply_move` は `score` を触りません（`hash` は自分で更新します）
- `enum_moves` が 0 を返したらその状態は終端です

**`undo_move` の書き方**：`apply_move` は必ず入れ子（DFS）で呼ばれるので、
`apply_move` の中で「元に戻すのに必要な情報」をグローバルなスタックに積み、
`undo_move` で pop するのが定石です（デモの `g_undo_pos` / `g_undo_mark` が実例）。

**評価値 ≠ スコア**：`State::score` は探索の順位付けに使う「評価値」です。
真のスコアと違う評価にして構いません（デモは「集めた価値 + `FUTURE_W` × 現在地の未訪問隣接数」を
評価値にしていて、`FUTURE_W` を optuna で調整します）。真のスコアは最後に手順を再生して求めます。

## 4. 最大化 / 最小化 の切り替え

`main.cpp` の 4 節で、使う方だけ残してもう一方をコメントアウトします。

```cpp
constexpr bool MAXIMIZE = true;        // ← スコア最大化（デモはこちら）
// constexpr bool MAXIMIZE = false;    // ← スコア最小化
```

`if constexpr` で分岐が消えるので実行時コストはゼロです。
`optimize.py` の `get_direction()` と `pahcer_config.toml` の `objective` も合わせてください。

## 5. パラメータ調整（optuna + pahcer）

C++ 側は環境変数 `p1, p2, ...` を読み、無ければ既定値を使います。**そのまま提出して大丈夫です。**

```bash
python3 tools/gen.py 0 20          # テストケースを用意（実際の AHC では公式 tools を使う）
cd 1_beam_search
vim pahcer_config.toml             # 問題に合わせて書き換え
python3 optimize.py                # → best params = {'p1': 18000, 'p2': 0.7}
```

手動で 1 回試すだけなら `p1=3000 p2=0.5 ./a.out < in.txt` でも上書きできます。

### ビーム幅の決め方

`BEAM_WIDTH`（p1）が最重要パラメータです。`ADAPTIVE_WIDTH = true`（既定）のときは
**基準値**として使われ、残り時間に応じて `[BEAM_WIDTH/4, BEAM_WIDTH*2]` の範囲で毎ターン自動調整されます。

- 実行後に `[hint]` が出る（時間が余っている）→ `BEAM_WIDTH` を上げる
- 上げても余る → `BEAM_CAP`（静的配列の上限）も上げる
- 時間切れが怖い → `ADAPTIVE_WIDTH` が終盤に幅を絞るので、基本は放っておいて良い

固定幅にしたい場合は `ADAPTIVE_WIDTH = false` にすると `BEAM_WIDTH` そのままで走ります。

## 6. 高速化のためにやっていること

| 箇所 | 内容 |
|---|---|
| 上位 W 個の選抜 | `priority_queue` を使わず **`nth_element`**。候補数を n として O(n)（ソートなら O(n log n)、優先度付きキューなら状態のコピーも発生） |
| 重複除去 | **オープンアドレス法 + 世代スタンプ**。毎ターンのクリアが不要。同じハッシュなら良い方だけ残す O(n)。テーブルは候補数の 4 倍を自動確保 |
| メモリ確保 | 候補配列・状態バッファはすべて**静的確保**。探索ループ中に `malloc` を一度も呼ばない |
| 状態バッファ | 2 面をピンポンで使い回す（毎ターンの確保・解放なし） |
| 手順の復元 | **参照カウント付きの履歴ツリー**。ビームから外れた枝は即座に回収されるので、ターン数×幅のメモリを持たずに済む |
| 差分更新版 | State のコピーが 0 回。木を Euler tour で辿り `apply_move` / `undo_move` で状態を作り直す。死んだ枝はツアー再構築時に刈る |
| chokudai | ヒープは `(スコア, プール添字)` だけを持ち、State をコピーしない。プールが尽きたら各深さの上位だけ残して回収（GC） |
| 時間計測 | x86 は **rdtsc**、ARM は **cntvct** を直読み（`chrono` の約 1/10、実測 0.25ns vs 12ns）。x86 は TSC 周波数を自動較正 |
| 計測頻度 | ビームサーチは **1 ターンに 1 回**、chokudai は 16 深さに 1 回だけ |
| その他 | 最大化/最小化は `constexpr` + `if constexpr` で実行時分岐ゼロ。候補構造体は 24 バイトに詰めて cache に載せる |

## ハッシュと候補数の自動検証（`[check]` だけでは足りない）

ビームサーチの `[check]` は「探索の評価値」と「真のスコア」を比べますが、この 2 つは
**そもそも一致しなくて良い**（`calc_score` に先読み項を入れるのが普通）ので、次のバグは検出できません。

- **`calc_hash()` が `apply_move()` 後の `state.hash` と食い違う**
  → 別物の状態を「重複」と誤判定して捨ててしまい、探索が静かに弱くなる
- **`enum_moves()` が `MAX_BRANCH` を超える数を書き込む** → 配列外書き込み（最悪クラッシュ）

そこで `main` の最初に `verify_state()` が走り、この 2 つを 1 手ずつ突き合わせます。

```
[verify] ハッシュと候補数 OK (300 手を検査)                                     ← 正常
[verify] NG 1 手目: calc_hash=edbb... / apply_move 後の hash=4fe2...            ← バグあり
[verify] ★enum_moves が 88 個返しました。MAX_BRANCH=64 を超えています          ← 配列外書き込み
```

乱数の状態は前後で復元するので、`VERIFY_MOVES` を変えても探索結果は変わりません。
提出時に消したければ `VERIFY_MOVES = 0` にしてください。

## 7. 注意点

- **`BEAM_CAP` はメモリに直結**：通常版は `sizeof(State) × 2 × BEAM_CAP` の静的メモリを使います。
  State が 1KB なら `BEAM_CAP = 32768` で 64MB です。問題に合わせて必ず調整してください。
  （差分更新版は State を 1 個しか持たないのでここは効きません）
- **`MAX_BRANCH`**：1 状態から出る遷移の最大数。候補配列のサイズ `BEAM_CAP × MAX_BRANCH` に直結します。
  実際より小さいと配列外書き込みになるので、必ず正しい値にしてください。
- **ハッシュの衝突**：`calc_hash` は Zobrist（64bit）を想定しています。衝突すると良い状態が消えます。
  重複除去が不要な問題（同じ状態に別経路で到達しない）なら `USE_HASH_DEDUP = false` にすると少し速くなります。
- **chokudai のメモリ**：`POOL_CAP × sizeof(State)` を確保します（既定 131072 個）。
  足りなくなったら各深さの上位 `POOL_CAP/(4×ターン数)` 個だけ残して自動で回収します。
- **`float` の精度**：評価値が 1e7 を超えるような問題では精度が足りません。`[check]` がずれ過ぎるようなら
  `State::score` と `calc_score()` の戻り値を `double` にしてください。
- **時間制限**：`TIME_LIMIT_MS`（既定 1900ms）は実行時間制限から余裕を引いた値にします。
- **1 と 2 はアルゴリズムが同じ**：まず 1 で書いて `[check]` が通ることを確認し、
  コピーが重いと分かってから 2 に `undo_move` を足して移植するのが安全です。
